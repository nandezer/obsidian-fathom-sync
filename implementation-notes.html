Implementation Notes — obsidian-fathom-sync

A running log of non-trivial design decisions, deviations, tradeoffs, and open questions. Append dated entries; do not rewrite history. See CLAUDE.md § "Running implementation notes" for the policy.

2026-05-21 — Import meeting from Fathom link

Feature: paste a Fathom URL or recording_id into the settings tab and import that single meeting's summary + transcript as if it were one of yours, even when the recording lives outside your workspace (public share link).

Decision Two-tier resolution for arbitrary inputs

The plugin's existing sync paths only ingest meetings that appear in /meetings. Single-link import accepts three input forms (numeric recording_id, /calls/{id-or-token} URL, /share/{token} URL) and falls back through up to four resolution paths:

  1. Workspace path — meeting is in the user's filtered /meetings list → process normally with full API content.
  2. API stub path — recording_id is API-accessible (workspace-shared) but excluded by the user's filters → fetch summary + transcript via existing getSummary/getTranscript, write a stub-metadata note tagged import_source: pasted-link.
  3. Share-token scrape path — only the share URL works; /recordings/{id} returns 404 because the recording isn't in the user's account. Scrape the share page's Inertia.js data-page attribute for metadata + lazy-load the AI summary via Inertia partial-data + pull the transcript and action items from the page's signed "copy" URLs. Tagged import_source: shared-link-scraped.
  4. Hard error — token revoked or Fathom changed the share format → directed MeetingNotFoundError / SharedRecordingNotAccessibleError Notice explaining what failed.

Deviation Approved plan said "find in /meetings with NO filters"; shipped uses the user's filters

The approved plan ([[plans/i-want-to-add-linear-volcano.md]] at findMeeting) called for an unfiltered /meetings search so the import could match meetings the user's filters exclude. In practice, Fathom's /meetings endpoint returns HTTP 500 with an HTML error page when called without any filters on accounts with many recordings. Walking around it by applying the user's existing syncTeams/recordedByFilter filters:

  • Eliminates the 500 (validated empirically against Marc's account, ~292 notes).
  • Reduces the import's blast radius — for recording_ids outside the filter, the list lookup misses cleanly and we fall through to the stub path (which was always going to handle that case anyway).
  • Trade-off: share-token URLs whose target is outside the filter never match in step 1, but step 3 (share-page scrape) handles them, so the user-visible result is unchanged.

Decision Share-page scraping uses Inertia.js, not generic HTML parsing

Diagnostic logging revealed Fathom's share pages are Inertia.js with component page-call-detail. The full page state is bundled into <div id="app" data-page="…"> as HTML-escaped JSON. Three extraction strategies in fathomApi.ts:

  • extractRecordingIdFromShareHtml — three progressive regexes (<link rel="canonical"> → og:url → bare /calls/{n}). Most authoritative first.
  • extractInertiaPageData — finds data-page, HTML-decodes, JSON.parses.
  • extractScrapedCall — pulls props.call fields (title, byline, started_at, duration_minutes, host.email, company.name, topic).

Decision Inertia partial-data probe for the AI summary

The initial Inertia props don't include the AI summary — it's a lazy prop. We send a follow-up request to the same share URL with headers X-Inertia: true + X-Inertia-Partial-Component: page-call-detail + X-Inertia-Partial-Data: aiNotes,…. Empirically, Fathom returns aiNotes with shape { defaultNote: { …, noteText: string, … }, notes, templates, isMeetingTooShortForSummary, … }. The summary markdown is at aiNotes.defaultNote.noteText.

Walker (extractInertiaSummaryFromValue) checks an ordered set of content-bearing keys including noteText, plus the isMeetingTooShortForSummary flag (surfaces a directed message when Fathom didn't generate a summary). Logs the inner shape on failure so future Fathom schema changes are easy to diagnose without exposing meeting content.

Decision Attendees derived from transcript speakers (not the API)

Fathom's share-page Inertia props expose only the host, no invitee list. The transcript names every speaker who talked, so deriveAttendeesFromSegments dedupes those into a synthetic FathomInvitee[] with empty email/email_domain. Downstream buildSummaryNote only reads .name, so the stub fields are inert.

This forced a small refactor in processScrapedSharedImport: the transcript is fetched before the meeting object is constructed, even if syncTranscripts is off. The needTranscript setting now only gates whether the transcript note is written; the transcript text itself is always pulled for attendee derivation.

Decision noteText anchor-tag conversion

Fathom's noteText embeds click-to-jump anchors: <a class='cursor-pointer' data-timestamp="72.0">text</a>. These render as plain text clutter in Obsidian. convertFathomNoteTextLinks rewrites each one to [text](https://fathom.video/calls/{id}?timestamp=72) so the click-to-jump still works (browser opens Fathom at the right offset).

Decision Single-flight mutex generalised, not refactored

The approved plan suggested refactoring triggerSync(mode, trigger) to take a discriminated operation object. Shipped a smaller change instead: a private withMutex(task) helper that returns true if the task ran and false if another op was in flight. Sync callers piggyback (await the existing op — same work); the import caller refuses (the in-flight is a sync, not the import the user asked for, so Notice + abort). Zero blast-radius on the three existing call sites (ribbon, two commands, setInterval).

Trade-off Inertia probe vs. content scraping

Considered HTML-scraping the rendered share page for summary content. Rejected because the page is a JS-shell SPA (~14KB body) — content only appears after JS runs, which requestUrl can't do. The Inertia partial-data protocol is Fathom's own SSR-bypass; we ride it instead.

Trade-off 500 added to retry list

Fathom's /meetings endpoint and signed-share-resource endpoints empirically return transient 500s with HTML error bodies that clear on retry (witnessed multiple times during testing). Added 500 to both the API call() retry list and fetchSignedShareResource's retry list with the same 2s/4s/8s backoff as 5xx. Risk: masks genuine application errors. Mitigation: we don't retry forever (4 attempts max), and the final failure still surfaces the original status.

Trade-off Action items endpoint regularly 500s persistently

Some meetings' clipboardActionItemsUrl returns 500 on every retry (Fathom backend bug, not transient). Current behaviour: 4× retry, log a warn, write the note without an action-items section. Considered shorter retry but kept full backoff because some 500s ARE transient.

Decision Custom error classes with Object.setPrototypeOf

Defined UrlParseError, MeetingNotFoundError, SharedRecordingNotAccessibleError for directed Notice mapping in main.ts:noticeImportError. Each constructor calls Object.setPrototypeOf(this, X.prototype) as defensive insurance: at tsconfig target: ES2018 some downlevels of class extends Error historically lost the prototype chain, breaking instanceof. Existing FathomApiError doesn't do this and works fine in practice (esbuild preserves native class syntax at ES2018), but the cost of adding it is trivial.

Decision URL parser is ASCII-strict and length-capped

src/utils/fathomUrl.ts validates numeric ids with /^[0-9]+$/ (not \d, which matches Unicode digits that Number() casts to NaN) and rejects inputs over 500 chars. Token regex character class is [A-Za-z0-9_-]{1,200} — tight enough to prevent ReDoS-style backtracking. 28 unit tests in tests/lib/fathom-url.test.ts cover the boundaries.

Decision Settings UI placed in the existing "Actions" section

Reviewer feedback (ui-designer) said the import control is a one-off trigger, so it belongs alongside "Run full sync" and "Reset sync cursor", not between "Filters" and "Webhook intake". Followed that. Empty input is no longer guarded in the button — it flows through to parseFathomReference → UrlParseError("empty") → directed Notice, so all parse feedback comes from one source.

Decision Command palette opens settings, no Modal

Considered shipping a one-input Modal for the command-palette entry. Chose to use Obsidian's internal app.setting.open() + openTabById(this.manifest.id) instead — 4 lines vs ~20 for a Modal subclass. Typed via the new src/obsidian-augments.d.ts module augmentation so there are zero @ts-ignore markers anywhere in src/. Defensive runtime check + Notice fallback if app.setting is unavailable on a future Obsidian version.

Open question Action-items endpoint persistent 500

For the Solidaridad/Planboo test meeting (recording_id 680923773), clipboardActionItemsUrl 500s on every retry. Unclear whether this is meeting-specific (no action items detected → bug returns 500 instead of empty) or a wider Fathom backend issue. To revisit: try a meeting that's known to have action items in the Fathom UI and see if the same URL works.

Open question Other note templates exposed by aiNotes

aiNotes includes templates: array(16) and notes: array(N). We only read defaultNote.noteText. If Fathom supports multiple templated notes (e.g. "sales-call summary", "product-review summary"), there may be richer content in notes[*]. Not investigated — the default note's content was sufficient for Marc's needs.
